# Audited campaign planning repair

`POST /api/campaigns/{id}/execution/replan` requests a correction from the campaign's existing planner. It does not replace a failed dispatch with a success receipt, instantiate an operator-authored DAG, or retry a published business card.

The operator must pause the campaign and supply its current revision, a stable request ID, the captured failure ID, and independently verifiable evidence. Owned dispatches, active sessions, queue runs and cleanup tasks must have settled. Ordinary recovery requires captured server evidence reporting no external effect requiring reconciliation. An external planning rejection that was independently audited as never attempted may use the explicit audit described below; no failure label clears an effect hold automatically.

For infrastructure/unknown failures, an explicit execution reconciliation hold and exactly one unreconciled execution failure are required. A captured `plan` failure in business artifact work may instead carry a source correction when there is no hold or only an evolution-budget hold. This branch requires zero unresolved infrastructure/unknown failures and the same terminal blocked receipt, active graph, unpublished descendants and artifact-only scope checks. It cannot approve an artifact, change an accepted contract, clear an effect hold or create a correction from a healthy task. The evidence remains an input for the existing planner and independent QA; a claimed policy mismatch is never itself approval.

If an agent has already proposed an unexecuted successor, a source-correction request may explicitly provide `supersede_candidate: {"version": 6, "digest": "<actual 64-character SHA256>"}`. The server requires the sole latest candidate/validated graph, its exact digest and active parent, no template binding and no published business work for that successor. It retains the graph and every original planner/QA receipt while marking that successor rejected. Omitting this field still rejects another pending candidate; infrastructure/unknown failures cannot use this option. The operator cannot supply a replacement DAG or approval. After resume the existing planner authors a new candidate, charged to the existing finite lifetime budget, and independent QA must validate it.

Supported failures are a completed, blocked, unaccepted artifact-only task in the active graph with no published descendants, a terminal failed validator of the latest unexecuted candidate, or the latest terminal planner for the preserved active graph with no pending successor. Planner recovery requires the same unknown/infrastructure reconciliation, settled ownership and explicit no-effect evidence; it creates a new planning identity rather than redispatching the cancelled card. A first candidate requires no prior business task or scheduled occurrence. A successor candidate must retain the current active parent and have no business task of its own; previously accepted root contracts remain immutable, while new roots require artifact-only inspection. This lets an interrupted control turn return to the existing planner without discarding accepted parent work. Failed external-effect tasks, malformed work receipts and unrelated newer candidates remain held.

For a completed external task whose native receipt is blocked with `failure_category: plan`, the optional `unattempted_effect: {dispatch_id, result_sha256, audit_sha256}` records an explicit operator attestation that the action was never attempted. The operator must audit the full captured command sequence, executable driver source and current remote/effect state first, retain the audit artifact, and supply its SHA256 in `audit_sha256` with a reviewable location in `evidence`. `result_sha256` hashes the exact UTF-8 stored dispatch result (`result::text`), not a reserialized provider file. The server checks that dispatch is the latest attempt for the same failed external task in the active graph, validates native capture provenance and the blocked planning receipt, and requires the sole unresolved failure, paused revision CAS, settled ownership and unpublished descendants. Hash pins identify the exact material; they do not independently prove the operator's effect assessment. Missing receipts, uncertain attempts, healthy tasks and non-planning execution failures cannot use this branch.

The audit is appended to the new planning failure. The original unknown category, external-effect evidence, provider result, graph, assignment, observations and usage are preserved byte for byte. The API does not approve an external outcome, stage an operator-authored graph or redispatch the failed card. After resume the existing planner must inspect the audited non-attempt, preserve already completed effects and produce a new contract requiring independent QA. Unknown or attempted effects remain outside this narrow recovery branch.

The transaction preserves the original goal's objective, success conditions, constraints, repository, executors and schedule. It appends reconciliation evidence and a planning failure linked to the original task. The original graph, receipt, failure, artifacts and cumulative usage remain available. For a failed validator, only its latest candidate is marked rejected; rejection is not approval. An optional monotonic finite budget increase is audited in `campaign_goal_revisions`, retains the node timeout and tool-limit mode, and never resets usage.

The campaign remains paused after the request. An identical request ID and body is idempotent across reconnects; changed content is rejected. After explicit resume, the existing native tick publishes a repair planning card to the existing planner. A different agent must validate the new candidate before activation or business publication. Published task identities and contracts remain immutable; a changed failed contract needs a new task key.

A terminal failed or cancelled artifact-only work dispatch with a missing result can request the same audited planning repair when its captured failure is unknown or infrastructure, explicitly requires no external-effect reconciliation, has no successful receipt claim, and has no published dependent work. The original failed dispatch, missing result, unknown classification, immutable artifacts and cumulative usage are preserved. This does not accept a recovered proposal or replay business work. Existing repeated-failure holds from older releases are admissible only with the same artifact-only safeguards; new execution failures retain their execution-reconciliation hold rather than losing it to a repeated-failure hold. Live owners, pending cleanup, additional unresolved outcomes and possible external effects still block this path.

Initial enrollment retains the three-evolution maximum. Explicit audited lifetime budget increases can allow up to sixteen evolutions, within the existing dispatch, elapsed-time and tool-call caps. Actual planning attempts and versions remain charged to the lifetime allowance, including failed attempts. Automatic execution cannot grant itself a budget increase.

The reconciliation tick observes terminal results even while a campaign is paused, without publishing work. A late, schema-valid assessment matching a digest-pinned operator-retired candidate is recorded as superseded, never as approval or a new planning failure. Its original provider result remains available. A pending or terminal-unobserved planner blocks admission of another control turn, so checking the next turn's evolution allowance cannot cancel an already-issued plan. Every repair prompt also receives the latest audited operator source-correction input for that campaign; later control errors do not hide it, and it remains evidence for independent verification rather than authority to approve a business action.

```json
{
  "expected_revision": 8,
  "request_id": "source-verified-business-repair-v1",
  "failure_id": "captured-failure-id",
  "evidence": "Original source requirements and current effects independently checked; preserve the failed attempt and complete the unchanged business objective."
}
```

The response identifies `revision`, `repair_failure_id`, `planner_agent_id`, `goal_scope_preserved` and `independent_validation_required`. The existing `/execution` inspection provides the preserved records and audit chain. This operation does not change the default ten-sample template-promotion threshold or combine unrelated campaign families.

The repository-scoped GitHub helper supports fixed reads: `review-threads <PR>`, `check-details <PR>`, and `feedback <PR>`. They capture the current PR head, unresolved thread state, failed check annotations and repository-scoped job details. `feedback` pages through every issue comment and PR review, preserves the provider IDs, bodies and timestamps, reports fetched/total counts, and rechecks head, base, state, update time and counts after pagination. Its `read_evidence` also preserves each exact CLI argument list and unmodified parsed provider response, including page cursors and the final recheck, so QA can audit the summaries against actual inputs. It bounds each connection to ten pages and the complete report, including raw evidence, to 4 MiB. A normal `view --json comments,reviews` does not attest complete feedback pagination; independent effects must also consume complete `feedback` and `review-threads` evidence. Head drift, permission failures or incomplete pagination cannot establish a successful business result. Required checks still use the existing `checks <PR> --required` command. Arbitrary API paths, other repositories, authentication commands, admin bypass and branch deletion remain unavailable.
